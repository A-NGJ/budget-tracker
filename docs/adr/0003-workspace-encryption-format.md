# Workspace encryption format

The workspace uses one random AES-256-GCM workspace key for every record. Record ciphertext never depends on a credential. Each decryption credential stores a key slot: a copy of the workspace key wrapped by a key derived from that credential. The passphrase slot uses PBKDF2-SHA256, 600,000 iterations by default, a 16-byte salt and an NFC-normalized passphrase of at least 12 characters. Readers refuse fewer than 100,000 iterations, so a tampered header cannot weaken key derivation. The recovery key and passphrase changes (issue #15) add or rewrap a slot. They do not re-encrypt records or require a re-import. We use only Web Crypto primitives available in current Chrome, Edge, Firefox and Safari. We rejected Argon2, which would need a WebAssembly dependency, because the slot format can add a `kdf` value later.

Every record and key slot has a format version and the workspace key id. AES-GCM additional authenticated data binds each key slot to `uid/slot/keyId` and each record to `uid/collection/recordId/keyId`. Ciphertext copied to another account, collection or document fails to decrypt. Firestore stores the header at `workspaces/{uid}` and records as envelopes `{formatVersion, keyId, iv, ciphertext, updatedAt}` beneath it. Security rules enforce ownership and envelope shape, so plaintext fields are rejected even if client code regresses.

The unlocked workspace key is non-extractable and lives only in memory. Locking, the 15-minute inactivity timeout and sign-out discard it. Firestore uses its in-memory cache only, so the browser never persists records, readable or encrypted. Sign-out also clears the persisted Firebase Auth session. Firestore uses long-polling transport because the streaming transport stalled in WebKit during emulator tests, and the workspace makes only one-shot reads and writes.
